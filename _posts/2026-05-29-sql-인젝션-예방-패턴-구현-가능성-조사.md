## **1. 배경**


일반 웹 앱의 SQL 인젝션은 **외부에서 들어온 입력값** (예: 검색어, URL 파라미터) 을 SQL 안에 넣을 때 발생합니다. 그 경우에는 **prepared statement / parameter binding** 으로 100% 차단이 가능합니다.(입력값을 SQL 구조에 못 끼게 막는 방식)


이번 프로젝트의 데이터 쿼리 기능과 다른 점:

- **사용자가 SQL 자체를 의도적으로 작성** (예: `SELECT * FROM r_report.report_master WHERE ...`)
- 그 SQL 이 그대로 DB 에서 실행됨
- 즉 입력값을 차단하는 것이 불가능

## **2. 업계 도구 사례**


| **도구**                              | **보안 패턴**                                                                       |
| ----------------------------------- | ------------------------------------------------------------------------------- |
| **Metabase**                        | 별도 read-only DB 사용자 / `{% raw %}{{{% endraw %}var{% raw %}}}{% endraw %}` placeholder 시스템 (값은 별도 binding) / query timeout |
| **Apache Superset**                 | DB-level safe mode (DML 금지 옵션) / per-DB read-only 사용자 / 위험 statement parsing 차단 |
| **Redash**                          | query runner 가 별도 read-only 계정 사용 / `{% raw %}{{{% endraw %}param{% raw %}}}{% endraw %}` placeholder / row limit         |
| **JasperReports / Crystal Reports** | `:param` / `$P{param}` parameter binding / 별도 DB 사용자 / 디자이너 권한을 BI 개발자에 한정      |
| **오즈리포트**                           | 데이터셋 SQL + `:변수` parameter binding / 디자이너 안에서만 SQL 작성                           |


공통 패턴: **1. 권한 격리 2. parameter binding 3. 자원 제한**


## **3. 방어 패턴 5가지**


### **1. 권한 격리**


별도 DB 사용자를 만들고 최소 권한만 부여하는 방식입니다.


사용자가 어떤 SQL 을 던지든 DB 레벨에서 차단됩니다.


{% raw %}
```sql
-- PostgreSQL 예시
CREATE ROLE r_report_query LOGIN PASSWORD '...';
GRANT CONNECT ON DATABASE r_report_db TO r_report_query;
GRANT USAGE ON SCHEMA r_report TO r_report_query;
GRANT SELECT ON r_report.report_master, r_report.data, r_report.component_master TO r_report_query;
-- INSERT/UPDATE/DELETE/DDL 권한 부여 안 함
-- 다른 schema (e.g. public, pg_catalog) 접근 차단
ALTER ROLE r_report_query SET search_path TO r_report;
```
{% endraw %}


### **2. Read-only transaction + Statement timeout**


{% raw %}
```javascript
await db.tx({ mode: 'READ ONLY' }, async (t) => {
  await t.none('SET LOCAL statement_timeout = 5000');  // 5초
  return t.any(userSql, params);
});
```
{% endraw %}

- DML 시도 자체가 차단 (PostgreSQL 의 read-only 모드 사용)
- 5초 넘으면 자동 abort (거대 쿼리로 DB 다운시키는 사고 방지)

### **3. Parameter binding (값 안전 처리)**


사용자가 SQL 본문은 작성하되 값은 placeholder 로 분리하는 방식입니다.


{% raw %}
```sql
-- 안전한 패턴 (사용자가 빌더에서 입력)
SELECT name, value FROM r_report.data
 WHERE kind = :kind AND name LIKE :pattern

-- 위험한 패턴 (사용자가 값을 SQL 안에 직접 넣음)
SELECT name, value FROM r_report.data
 WHERE kind = 'static' AND name LIKE '%문자열_concat%'
```
{% endraw %}

- pg-promise (PG) / oracledb (Oracle) 둘 다 `:name` 형식 named parameter 지원
- 빌더 UI 가 SQL 본문 입력란 + 변수값 입력란을 분리해서 사용자가 string concat 하지 못하게 강제

### **4. 자동 LIMIT 강제**


사용자가 LIMIT 안 넣었으면 자동으로 부여:


{% raw %}
```javascript
const limited=/\blimit\s+\d+/i.test(userSql)? userSql:`${userSql} LIMIT 10000`;
```
{% endraw %}


### **5. SQL parser 사전 검증**


`node-sql-parser` 같은 라이브러리로 SQL 을 AST 로 파싱 후 검증:


{% raw %}
```javascript
const parser = new Parser();
const ast = parser.astify(userSql);
if (ast.type !== 'select') throw new Error('SELECT 만 허용');
```
{% endraw %}

- 장점: DB 도달 전에 차단해서 DB 부하 줄임
- 단점: parser 가 모든 SQL 방언 (PG vs Oracle) 을 정확히 처리 못 할 수 있음
- 1. 권한 격리의 보조 수단

## **4. 추가 고려 사항**

- 데이터 권한 정책 (사용자별 / 부서별 어떤 컬럼 / 테이블 보기 가능) - 별도 권한 모델 sub-project
- 민감정보 컬럼 마스킹 - view / column-level GRANT 로 처리
- 쿼리 결과 캐싱 - PDF 렌더링마다 매번 실행할지 / TTL 캐시 둘지
- 다중 페이지 / 페이지네이션
- HCCC Oracle 의 사내 인사 DB / 다른 사내 ERP DB 통합 - 권한 모델 + 네트워크 정책 별도 검토

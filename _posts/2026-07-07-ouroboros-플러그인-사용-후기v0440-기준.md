코드 파일 13개, 테스트 코드 파일 14개를 생성한 작업으로 대화형 세션 사용 시 설계부터 구현, 테스트까지 2시간 정도 소요 예상되는 작업 기준으로 작성


### 실행 시간 분석


실측 데이터

- 인터뷰 → Seed 생성까지 약 1시간 37분이 소요되었고 실행 단계(서브 AC 단위) 소요 시간은 약 2시간

    | AC 1 | 1.1     | 23.6  |                  |
    |      | 1.2     | 11.7  |                  |
    |      | 1.3.1   | 10.3  |                  |
    |      | 1.3.2   | 10.1  |                  |
    | AC 2 | 2.1.1   | 4.8   |                  |

오래 걸리는 구조적 이유

- 서브 AC마다 새 Claude Code 프로세스 기동 (세션 재사용 불가)
→ 에이전트마다 작업 디렉토리 재탐색, 파일 재탐색
- AC마다 depth 를 나눠야 할 지 판단하는 별도 LLM 호출 (건당 30초~5분)
- 서브 AC마다 프로젝트 전체 테스트 실행, real ollama 통합 테스트가 포함되면 로컬 추론 시간도 누적
- 의존성 있는 AC는 순차 실행
    - 당연한 말이지만 `max_parallel_workers` 3이어도 서로 의존성이 없는 작업만 병렬 실행 가능
    - 따라서 병렬 실행을 원한다면 인터뷰 시에 AC 를 독립적으로 설계 필요

컨텍스트 전달 방식 (LevelContext)

- 완료된 AC의 요약을 다음 레벨 에이전트 프롬프트에 Previous Work Context 섹션으로 주입
- 요약 내용: AC 설명 앞 60자, 수정 파일 경로 최대 5개, 수정 파일에서 추출한 public API 시그니처, 최종 메시지 꼬리(truncate), 전체 총량 상한선
- 파일 경로와 시그니처만 전달되므로 실제 파일 내용은 다음 에이전트가 다시 읽어야 함
→ 대화형 세션 대비 재탐색 비용이 남는 이유

시간 단축 설정 (`~/.ouroboros/config.yaml`)


{% raw %}
```yaml
evaluation:
  stage3_enabled: false          # 다중 모델 합의 비활성

execution:
  max_iterations_per_ac: 5       # AC당 재시도 상한 (기본 10)

resilience:
  wonder_model: claude-sonnet-4-6   # 기본 opus → sonnet
  reflect_model: claude-sonnet-4-6

runtime_controls:
  generation_safety_timeout_seconds: 14400   # 전체 작업 시간 상한시간
```
{% endraw %}

- Stage 3 합의는 최소 3개 모델 투표에 advocate/devil/judge 왕복까지 도는 단계로 사용자 개입 없이 정확한 결과물을 내기 위해서는 필요한 옵션이지만 시간 단축을 원한다면 false 처리 가능

### 트러블슈팅 사례


`'NoneType' object has no attribute 'strip'`

- 실행 중 MCP 서버 재시작 후 세션 재개 경로에서 백그라운드 잡 전체가 `RuntimeError: Seed execution failed: 'NoneType' object has no attribute 'strip'`으로 죽음
- 원인은 에이전트 결과 텍스트가 None인 경로에서 `.strip()` 호출. 같은 코드베이스에 `isinstance(content, str) and content.strip()`으로 방어한 지점과 `message.content.strip()`으로 방어 없는 지점이 섞여있었기 때문 (`runtime_message_projection.py:111`, `runner.py:2428` 등)
- `docs/rfc/config-coherence.md` 확인해보면 플러그인 개발자도 MCP 서버 재시작 시 문제가 발생한다는 사실을 인지하고 있는 것으로 보임
- 부가적으로 상위 핸들러가 `raise RuntimeError(str(result.error))`로 원본 예외를 문자열화해 다시 던지므로 스택 트레이스가 소실되어 정확한 에러 지점을 로그로 특정 불가
- 산출물은 디스크에 보존됨. 완료 AC 기록은 EventStore에 남으므로 재실행 시 이어가기는 가능
- 워치독/티어 승급/체크포인트 등 복원 계층은 갖췄으나 결과 파싱 기본 경로의 None 방어가 누락된 상태. 크래시 시 좀비로 남지 않고 잡이 실패로 종료되는 점은 확인

    > 💡 **워치독**  
    > 실행이 살아있는지 주기적으로 감시하는 장치로 멈춘 경우에만 중단  
    >   
    > **티어 승급**  
    >   
    > PAL Router 가 모델을 비용/성능에 따라 3단계로 나눠놓고 결과에 따라 조정하는 매커니즘  
    >   
    > **PAL Router**  
    >   
    > Progressive Adaptive LLM Router의 약자로 Ouroboros가 각 작업에 어떤 티어의 모델을 배정할 지 결정하는 엔진  
    >   
    > **체크포인트**  
    >   
    > 특정 시점의 실행 상태를 저장해둔 스냅샷으로 문제 발생 시 그 지점부터 다시 시작할 수 있게 하는 장치


로그와 데이터 위치


| 경로                                | 내용                           |
| --------------------------------- | ---------------------------- |
| `~/.ouroboros/logs/ouroboros.log` | 실행 로그, 실행이 도는지/죽었는지 1차 확인 지점 |
| `~/.ouroboros/ouroboros.db`       | EventStore, 모든 상태 변화 이벤트     |
| `~/.ouroboros/seeds/`             | 생성된 Seed 스펙                  |
| `~/.ouroboros/data/`              | 인터뷰 기록, 체크포인트                |
| `~/.ouroboros/config.yaml`        | 사용자 설정                       |

- 로그에서 `parallel_executor.ac.started` / `ac.completed` 이벤트로 진행 상황 추적, `duration_seconds`로 AC별 소요 확인
- `agent_process.work_failed` 트레이스백이 보이면 실행 사망. `Task was destroyed but it is pending!`, `sqlite3.OperationalError: no active connection`, `CancelledError`는 세션 취소/재시작 시점의 비동기 정리 잔여물로 실행에는 무해
- 훅 커맨드가 `python3`를 호출하므로 Windows에서 `python3`가 PATH에 없으면 훅이 조용히 실패할 수 있음

### 결론


위와 같은 플러그인 내부 서버 에러 등으로 봤을 때 아직 불안정한 부분이 있기는 하나, 시간이 오래 걸려도 괜찮은 작업을 백그라운드로 돌려놓는 용도로는 나쁘지 않을 것 같다고 생각함


하지만 낮에 사람이 붙어서 진행하는 작업에 사용하기에는 굳이라는 생각이 들었음 


그 근거는 다른 플러그인 대비 소요 시간이 길고 이를 단축하기 위해 사용자가 개입한다면 해당 플러그인을 사용하는 의미가 없다는 점이 있음


따라서 만약 사용한다면 인터뷰로 요구사항의 모호성을 수치화해 구체화하는 부분만 사용하고 대화형 세션으로 개발하는 방식이 더 효율적일 것으로 보임
